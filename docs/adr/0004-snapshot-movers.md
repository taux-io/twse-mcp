# `snapshot.movers`：漲跌幅排行的幾個決定

問「漲幅榜」「今天漲停幾檔」很自然，但現有工具答不好。這份 ADR 記錄 `snapshot.movers`
（#164）為什麼這樣排序、漲跌停怎麼推算、範圍為什麼只有上市股票、為什麼不做上櫃，
讓下一個人不必重新推一次。實作在 `src/core.ts` 的 `buildMovers`。

決定日期：2026-10-19。

## 依漲跌幅%排序，不是依漲跌額

上市個股日成交資訊（`exchangeReport/STOCK_DAY_ALL`）只有 `Change`（漲跌，單位是元）。
用 `dataset.get` 的 `sort_by: Change` 排出來的是「漲了幾元」，股價高的永遠排前面：
2026-10-16 川湖漲 235 元排第一，但只有 +2.42%；威鋒電子只漲 10 元，是 +10.00%。

- 漲跌幅% = 漲跌 ÷ 前收盤，前收盤 = 收盤 − 漲跌。資料集沒有這個欄位，所以自己算。
- 排序用未四捨五入的值，輸出才四捨五入到小數 2 位。前收盤 ≤ 0 的列跳過。
- 沒有做成 `dataset.get` 的選項：那支工具的設計是「資料集原樣回傳」，不計算衍生欄位。
  `dataset.get` 的描述改為指向 `snapshot.movers`，模型問排行時才不會自己排錯。

## 漲停與跌停是推算的

資料沒有漲跌停標記，所以用規則推算，並在回應的 `note` 說明這是推算：

- 漲停價 = 前收盤 ×1.1，依升降單位**無條件捨去**；跌停價 = 前收盤 ×0.9，依升降單位**無條件進位**。
  收盤 ≥ 漲停價算漲停，≤ 跌停價算跌停。
- 升降單位（依該價位）：未滿 10 元 0.01、10–50 元 0.05、50–100 元 0.1、100–500 元 0.5、
  500–1000 元 1、1000 元以上 5。
- 所以漲停不一定是 +10%：前收 94.5 的漲停價是 103.5（+9.52%），前收 960 是 1055（+9.90%）。
  只看漲幅 ≥ 10% 會漏掉它們。
- **全程用「分」的整數運算。** 價格乘 1.1、0.9 在浮點數會有誤差，收盤剛好等於漲停價時，
  誤差會把它判成「沒到」。把價格換成分（`Math.round(price * 100)`）後，乘 11 或 9 再除 10
  才取整，結果就精確。升降單位也以「分」表示。
- 已知沒處理的例外：新上市初期不設漲跌幅限制、處置股、減資恢復買賣等。遇到這些，
  推算的漲跌停可能與實際不同。

## 範圍只含上市股票

範圍是四碼、不以 0 開頭的代號（`/^[1-9]\d{3}$/`），與 `snapshot.market` 的漲跌家數用同一個判斷
（共用 `isListedStock`），兩邊數字才對得上。

- 不含 ETF（00 開頭）與權證：槓桿、反向 ETF 的單日漲跌幅動輒數個百分點，會把排行擠滿，
  而問「漲幅榜」的人通常指個股。
- 含少數存託憑證（四碼，例如 `-DR`）：它們在代號上與股票無法區分，與漲跌家數的處理一致。
- 分母是**全部**上市個股：漲停、跌停家數不受 `limit` 影響。

## 不做上櫃

使用者問過上櫃的漲跌幅排行，這裡不做，原因有三，任何一個沒解決都不該做：

1. **線上版連不到。** 櫃買中心在 IP 層擋掉 Cloudflare 的出口，連續轉址，沒有任何標頭組合可行
   （commit `419da94`，這個專案曾加過上櫃後還原）。這個結論是當時的紀錄，沒有重測。
2. **授權沒講清楚。** 櫃買中心 OpenAPI 頁面沒有授權條款；網站使用條款第五條禁止未經同意的自動下載，
   第七條只排除已授權給政府資料開放平臺的資料。個人查詢問題不大，做成對外服務就是另一回事。
3. **資料量。** `tpex_mainboard_daily_close_quotes` 一次回約 5 MB、12,587 列（大多是權證），
   沒有伺服器端過濾。2026-10-18 實測前兩次下載傳到一半就中斷。Workers 免費方案每個請求 10 ms CPU
   （#104），解析這麼大的 JSON 很可能超過；這點沒有實測。
   （2026-10-31 已升級 Workers Paid，HTTP 請求的 CPU 上限提高為預設 30 秒，見 [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)，
   CPU 不再是疑慮；下載中斷與沒有伺服器端過濾仍在。）

要重新評估，至少需要：取得櫃買中心的書面同意或確認資料在政府資料開放平臺上，且線上版出口能連上。
不建議想辦法繞過封鎖。若只是個人要用，本機 stdio 版的 MCP 工具不值得做：這個 repo 沒有 stdio 入口
（入口是 Worker，綁 D1），要另寫入口、打包與發佈，等於多一個產品面；發佈出去則每位使用者的 IP 都去打櫃買，
授權問題只是轉嫁。改做成一支獨立腳本（#174）。

### 個人用腳本：`scripts/tpex-movers.mjs`

`node scripts/tpex-movers.mjs [N] [--json]`（Node 23.6 以上，因為直接讀 `src/core.ts`）。
從自己的 IP 抓櫃買的 `tpex_mainboard_daily_close_quotes`，轉成證交所的欄位名後呼叫 `buildMovers`，
輸出上櫃漲幅與跌幅前 N 名與漲停、跌停檔數。

- **不是 MCP 工具，不進 CI、不發佈、不動 `package.json`。** 沒有測試：它只做欄位轉換，演算法由 `buildMovers` 的測試涵蓋。
- **授權限制照舊：** 只給自己偶爾查一次（一次一個請求，約 5 MB），不要排程、不要轉成對外服務。檔頭也寫了這點。
  它不解決上面三個理由中的授權與線上被擋，只是把風險限制在個人本機使用。
- 下載若傳到一半中斷會重試（最多 4 次）；這個重試只靠程式推演，沒有實際觸發過。

### 2026-10-21 重測（資料日期 2026-10-20）

動手前先對櫃買重測，確認算法能共用：

- **欄位對照：** `SecuritiesCompanyCode`、`CompanyName`、`Close`、`Change`、`TradingShares`
  → `Code`、`Name`、`ClosingPrice`、`Change`、`TradeVolume`；`Date` 同為民國格式。
- **範圍判斷：** 四碼代號 891 檔，全都不以 0 開頭；ETF 與權證是五、六碼，所以 `isListedStock` 不用改。
  22 檔的 `Close`、`Change` 是 `---`（沒有成交），會被略過。
- **漲跌停規則與上市相同。** 櫃買每天公布次日的漲停價與跌停價（`NextLimitUp`、`NextLimitDown`），
  拿它當獨立答案，用同一套升降單位與 ±10% 規則重算：891 檔裡 **890 檔吻合**。
  不吻合的 **7806** 公布為 9995／0.01，是新上市初期不設漲跌幅限制——這正是上面「已知沒處理的例外」；
  腳本遇到這類股票會標註其漲跌停推算不可信。
- 與另一套 Decimal 程式重算比對：漲幅前 10、跌幅前 10、漲停 24 檔、跌停 0 檔一致。
  兩邊用同一套規則，所以這證明實作與規則一致，不證明規則涵蓋所有例外。
- 5 MB 的檔案這次第一次就下載完整，先前（2026-10-18）則有兩次傳到一半中斷；是否穩定沒有結論。

## 驗證

- 2026-10-19 對正式環境呼叫一次（`limit=10`），與直接抓證交所上游、用獨立寫的 Decimal 程式重算的結果比對：
  漲幅前 10、跌幅前 10、漲停 19 檔、跌停 0 檔完全一致。兩邊用同一套漲跌停規則，
  所以這證明實作與規則一致，不證明規則涵蓋所有例外。
- 工具選擇（`eval:ab`，opus 與 sonnet 各一輪）：新增的三題改動後都選對 `snapshot.movers`，
  既有 54 題沒有退步，包含描述有改的 `dataset.get` 排名篩選題。
- 答案核對（`npm run eval:answers`，`scripts/eval-answers.mjs` 的三題，#168）：看模型有沒有照回應裡的 `note` 讀數字。
  標準答案取自同一次對話的工具結果；資料日期不是台北今天時，答案都要說出資料日期（不能當成當天盤中）。
  - `movers-gainers`、`movers-losers`：答案要有榜首的代號或名稱，以及它的漲跌幅%（誤差 0.01；跌幅榜比絕對值）。
  - `movers-limit-up`：答案要有正確的漲停家數（家數是 0 時，說「沒有」也算），並說明是推算值
    （「推算」「估算」「依前收盤／升降單位」「沒有標記」等字眼）。
  - 2026-10-21 本機結果：opus、sonnet 各 `EVAL_REPEAT=3`，三題共 18 輪全部通過，失敗、需人工看、沒驗到都是 0。
    讀答案原文：兩個模型都註明漲停 6 檔是推算、不含 ETF 與上櫃，也指出資料是 2026-10-19、10-20 可能是上游還沒更新。
  - 判分的限制：家數是比對「答案裡有這個整數」，可能被無關的數字碰巧對上；推算的說明只比對關鍵字眼，
    換一種講法會被判失敗——失敗時先讀原文，再決定是模型沒讀還是規則太嚴。
